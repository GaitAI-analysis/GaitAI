--------------------------------------------------------------------------------
SECTION B — CLOUD FIRESTORE (THE DATABASE)
--------------------------------------------------------------------------------
B1. Build → Firestore Database → Create database.
    - Mode   : PRODUCTION mode (not test mode — test mode expires and then
               everything breaks silently).
    - Region : your choice; asia-south1 (Mumbai) recommended for our audience.
    - Type   : Cloud Firestore. NOT Realtime Database.

B2. Do NOT pre-create any collections. They are created on first write.
    For reference, the frontend reads/writes exactly these paths:

    postComments/{postSlug}/comments/{commentId}   approved, public-readable
    pendingComments/{postSlug}/comments/{id}       canonical pending submissions
    pendingCommentQueue/{postSlug}__{commentId}    flat moderation queue mirror
    reportedComments/{reportId}                    reader-flagged comments
    posts/{postId}                                 (FUTURE — control-panel
                                                   content; see SECTION E)

B3. SECURITY RULES — this is the real enforcement layer, do not skip.
    - Open Firestore Database → Rules.
    - Paste the ENTIRE contents of the file `firestore.rules` from the repo
      root, then click PUBLISH.
    - The rules enforce: anyone may READ approved comments and CREATE a
      validated pending comment/report; ONLY the admin allowlist may read the
      pending queue, approve, reject, delete, or manage reports.

B4. The admin allowlist currently contains two emails, hardcoded in the rules:
        anubhaparashar1025@gmail.com
        gait.ai.founder@gmail.com
    If moderators change, edit the `isAdmin()` function in firestore.rules AND
    tell me, so I mirror it in src/lib/comments/config.ts (UI-side check).

--------------------------------------------------------------------------------
SECTION C — AUTHENTICATION
--------------------------------------------------------------------------------
C1. Build → Authentication → Get started.

C2. Sign-in method → enable GOOGLE provider only. (Moderation actions are
    gated on a verified Google account matching the allowlist in the rules.
    Public commenters do NOT need accounts.)

C3. Authentication → Settings → Authorized domains — make sure ALL of these
    are listed:
        gaitai.in
        www.gaitai.in
        localhost
    Missing domains = Google sign-in popup fails on that origin.

NOTE: The admin control panel currently runs WITHOUT login by frontend
decision (temporary). Auth will be re-attached before the panel goes live
against Firestore, using this same Google provider — so configure it now.

--------------------------------------------------------------------------------
The control panel manages the posts shown on /insights and /publications.
Today those posts are baked into the static build; the panel runs on local
data. To make the panel drive the live site we need:

E1. A `posts/{postId}` Firestore collection. Document shape (already fixed by
    the frontend types — do not rename fields):
        id, slug, title, category, summary, body, tags[], publishedAt (ISO),

        externalUrl (optional), attachmentUrl/attachmentName (optional)
    Categories: research | announcement | documentation | approval | blog | demo

E2. Rules for it (add to firestore.rules when we wire this):

E4. App Check (optional but recommended): enable with reCAPTCHA v3 for
